## Asset streaming: what the port already does

Texture streaming in the literal sense is already there; the missing part is *which* textures to
keep, not how to load them.

- Upload is lazy: an image is uploaded from guest memory when first used
  (`TextureCache::UploadImage`, `texture_cache.cpp:884`). Nothing is read from disk — the "disk" is
  the game's own memory.
- Per-mip hashes (XXH3) skip unchanged mips, but only for mips ≤ 64 KiB, GPU-modified images and
  storage/render/depth targets (`texture_cache.cpp:841`). A large static texture re-uploads whole
  after eviction.
- Eviction is a time-based LRU over an explicit list (`Image::lru_id`, `lru_cache`), advanced once
  per guest submission (`gc_tick`). `RunGarbageCollector` → `GarbageCollectImages`
  (`texture_cache.cpp:1114`, `:1332`).
- Ages: idle 20 s normally (`BB_GC_IDLE_SECONDS`), 5 s over the pressure mark
  (`BB_GC_PRESSURE_IDLE_SECONDS`), 1 s over critical, then a last-resort pass that takes anything.
- Thresholds: 70 / 85 / 95 % of VRAM; on integrated GPUs (and `BB_GC_BUDGET_MB`) of the driver's
  current budget instead.
- Eviction writes dirty GPU-written images back to guest memory first (`DownloadImageMemory`) when
  `SafeToDownload()`; tiled GPU-written images cannot be written back and are kept (they spill to
  system memory), because dropping them caused black screens (`BB_GC_DROP_OLD=1` restores the old
  behaviour and the bug).
- Bounded work per pass: 10 / 20 / 40 deletions, at most 256 images visited.
- Observability: a `Memory:` line every 60 s (VRAM, textures, backing memory, idle-by-a-minute,
  kept tiled images, process memory), a `Texture cache: memory pressure` line every 5 s, and
  `BB_VMA_DUMP=<file>` for the allocator's per-allocation stats.

No camera, distance or visibility signal exists anywhere in `video_core/texture_cache`; the only
"is it needed" signal is the LRU touch when a draw binds the image.

## What a real "asset streaming" feature would add

1. **Visibility/distance priority (small, in reach).** Mark images bound by this frame's draws as
   hot and let the collector evict cold ones first under pressure, instead of relying on 20 s of
   age. Hook: `GetImage`/`UpdateImage` already touch the LRU; the collector needs a "used in the
   last N frames" bit and a separate eviction queue. Must not touch images the game can read back
   (render targets) — that is the black-screen lesson above.
2. **Prefetch (medium).** Needs a predictor; the port has no access to the game's asset requests
   except through the draw stream and file reads (`runtime_file.c`). Could warm a texture's mips
   when an image of the same address range was used in the previous frame.
3. **Virtual texturing / partial mip residency (large).** Images are allocated with all mips and
   uploaded as one image; only buffers use sparse residency today
   (`VK_IMAGE_CREATE_SPARSE_*` appears in `buffer_cache`, not in the texture cache). Doing this
   properly needs sparse images plus a residency manager keyed by mip/tile, and shader-visible
   sampling of partially resident images. Multi-week, and the tile manager already detiles whole
   images (`tile_manager.DetileImage`), so the mip layout work is the real cost.

Recommended first step when work resumes: measure first (a 10-minute run in a dense area with the
`Memory:` lines and `BB_GC_BUDGET_MB` forced low) to see whether evictions are age-driven or
pressure-driven on the target card, then do (1) only if the logs show pressure evictions of
textures that were visible a moment ago.

## VRAM warning (added later the same day)

- `BbOverlay::Warn` (`gpu/shim/bbport_overlay.*`): ten-second amber banner at the top of the
  screen; `Visible()` and `Render()` know about it, input is not captured. Text is English, like
  the in-game menu.
- `TextureCache::GarbageCollectImages` warns when free VRAM < 1.5 GB (`BB_VRAM_WARN_MB`, 0 off),
  again each 256 MiB closer, re-armed once free rises above the threshold. Limit =
  `BB_GC_BUDGET_MB` if set, else the device-local total. Discrete GPUs only — on an iGPU the
  "limit" is system memory, not a crash. Log line: `VRAM: N MiB free of M MiB, warned the player
  to save`.
- Nothing is blocked: the game still fails when it truly runs out.
- Survey, ranking of optimization candidates and the measurement recipe:
  [`docs/VRAM_PERFORMANCE.md`](../VRAM_PERFORMANCE.md).
